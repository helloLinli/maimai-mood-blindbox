# MCP 工具调用配方

给执行 Agent 的速查表：每个工具**什么时机调、要拿什么、拿到后怎么用、失败怎么退**。

> **关于参数**：麦当劳 MCP 的官方工具清单与用途是公开信息，但各工具的请求参数 schema 本仓库无法完整核实。
> 下表「关键输入」一列是按官方工具描述推断的**示意字段**，实际以 MCP 返回的 schema 为准；
> 工具名、调用时机、依赖关系与降级策略是实际实现所依赖的部分。

## 必备调用

### `now-time-info` · 获取当前时间信息

| 项目 | 内容 |
|---|---|
| 调用时机 | 每次体验的第一步，与门店查询并行 |
| 关键输入（示意） | 无 |
| 拿到后怎么用 | `10:30 前` 判为早餐时段 → 选品池限定 `meal = breakfast / all`；日期进开盒种子；时间印在小票抬头 |
| 失败降级 | 用本机时间，并在小票标注时间来源 |

### `query-nearby-stores` · 查询附近可用门店

| 项目 | 内容 |
|---|---|
| 调用时机 | 到店场景，与时间查询并行 |
| 关键输入（示意） | 地址或经纬度（`address` / `lat` + `lng`） |
| 拿到后怎么用 | 取门店编码与名称；门店编码作为 `seedExtra` 进种子；名称印在小票上 |
| 失败降级 | 跳过下单，仅出小票并说明 |

### `query-meals` · 查询当前可售卖的餐品列表

| 项目 | 内容 |
|---|---|
| 调用时机 | 门店确定之后，**选品的唯一来源** |
| 关键输入（示意） | 门店编码 `storeCode`、就餐方式（堂食/外带/外送） |
| 拿到后怎么用 | 按分类归入主食/配餐/饮品/甜品四个池子；保留餐品编码供 `calculate-price` 与 `create-order` 使用 |
| 失败降级 | 切演示菜单，小票标注「演示数据」 |
| 注意 | 禁止凭记忆补餐品。菜单里没有的，一律不出现 |

### `list-nutrition-foods` · 餐品营养信息列表

| 项目 | 内容 |
|---|---|
| 调用时机 | 菜单到手之后，与详情查询并行 |
| 关键输入（示意） | 餐品编码列表（`productCodes`），或为空返回全量 |
| 拿到后怎么用 | 算每人热量与蛋白质，校验情绪目标与用户人均热量上限 |
| 失败降级 | 按品类估算（主食 300-650 / 配餐 70-430 / 饮品 0-210 / 甜品 120-320 kcal），小票标注「估算值」 |

### `calculate-price` · 商品价格计算

| 项目 | 内容 |
|---|---|
| 调用时机 | 3 个候选盲盒定稿后，**逐个试算** |
| 关键输入（示意） | 门店编码、餐品列表（编码 + 数量）、可选券 |
| 拿到后怎么用 | 得到商品金额 / 配送费 / 优惠金额 / 应付总价；**超预算的候选直接淘汰**；结余印在小票上 |
| 失败降级 | 用参考价并在小票标注；所有候选都超预算时反推最低预算 |
| 注意 | 「不超预算」必须是算出来的，不能靠估 |

## 按场景启用

### 外送场景：`delivery-query-addresses` → `delivery-query-stores`

先取用户已有地址；没有地址时用 `delivery-create-address` 新增，再查可配送门店。地址信息只用于本次查询，不写入日志、不印在小票上。

### 忌口与辣度：`query-meal-detail`

只对**最终可能入盒的餐品**调用（通常 2-4 件），用于确认套餐组成与可替换项。命中忌口的优先替换，换不掉就整件剔除。宁可少一个选择，也不要踩用户的忌口。

### 省钱：`auto-bind-coupons` → `available-coupons` / `query-my-coupons` / `query-store-coupons`

顺序固定：先一键领券，再并发查三个券来源，最后把可用券交给 `calculate-price` 试算。
三个查询互不依赖，可并发以省时间。若用户在「赶时间」情绪下，跳过活动类查询，只保留领券与算价。

### 活动彩蛋：`campaign-calendar`

查当月活动。命中当日活动时，在盲盒里加一句「今日活动彩蛋」并说明如何获得。
活动信息只做展示，**不要替用户判断能不能用**——能不能用由 `calculate-price` 说了算。

### 积分与激励：`query-my-account`

在给出小票的同时告诉用户「这单能得多少积分」，把积分放到决策现场。
可选扩展：`mall-points-products` 查可兑换商品 → `mall-create-order` 用积分兑换甜品加料。

### 下单：`create-order`

| 项目 | 内容 |
|---|---|
| 前置条件 | 用户**明确同意**下单，且 `calculate-price` 已成功 |
| 关键输入（示意） | 门店编码、就餐方式、餐品列表、联系方式 |
| 拿到后怎么用 | 把返回的订单号与支付链接原样交给用户；不要代为支付 |
| 失败降级 | 保留小票，说明失败原因并允许重试；不得重复创建订单 |

只读辅助：`query-order`（查订单状态）、`order-list`（历史订单）、`cancel-order`（用户要求取消时）。

## 调用纪律

1. **一次体验控制在 6-9 次调用**：营养数据一次拉取本地复用；详情只查最终入座餐品；券查询并发。
2. **限流 600 次/分钟**：收到 `429` 时指数退避重试一次；仍失败就复用本次已取数据，不要让用户重填一遍。
3. **`401` 表示 Token 无效**：立刻停止调用并切演示模式，同时提示用户检查 Token。
4. **事实与偏好分离**：MCP 提供事实（有什么、多少钱、多少热量），引擎提供偏好（该选什么）。事实必须来自 MCP，偏好必须可复现。
5. **不泄露与不回显**：Token、手机号、地址、支付信息一律不写入小票、日志或对话回显。
